How it’s built

Three systems, one job: get a student from “tickets just dropped” to the ticket page in about a second, and never ping them twice.

The shape of it

Pages in, one alert out.

Two watchers read public ticket pages and post what they see. The backend turns those observations into a state per night, decides what changed, and fans the change out to the people who follow that night: pushes to the iPhone app, web push and email to the website. Money moves through Stripe Connect.

The iPhone app

Native, all the way down.

  • SwiftUI, iOS 17 and up. On iOS 26 the tab bar is Liquid Glass, with a classic fallback below it.
  • Four targets: the app; a widget extension with the Tonight in Exeter widget and a Lock Screen / Dynamic Island countdown Live Activity; a notification service extension that downloads the night’s flyer into each push; and unit tests.
  • Pushes that break through. Drop alerts go out over APNs as time-sensitive notifications with action buttons (Get tickets, View night, Sell). A tap opens the ticket page directly, even on a cold launch.
  • StoreKit 2 for the plans. Each purchase carries the user’s account token, and every transaction is also posted to the server and verified with Apple there.
  • Passwordless sign-in: an email, then a six-digit code. The session lives in the Keychain.
  • Instant cold start. One catalogue store feeds every screen and is cached on disk; flyers go through a downsampling image pipeline with memory and disk caches.
  • London time, properly. Nights are grouped in Europe/London, and a 00:30 start belongs to the night before.
  • A privacy manifest, and no tracking: data is used to run the app.

The backend

Every night is a small state machine.

Next.js 15 and React 19 on Vercel, Postgres through Drizzle ORM. The website uses server actions; the iPhone app talks to a JSON API beside them.

Each night has a state (pending, live or sold out) driven by the watchers’ observations, and each change emits one of four alert kinds: announced, reminder, dropped, restock. The alert is written to an outbox in the same transaction as the state change, so a failed send is retried rather than lost, and fresh observations are applied before stale retries so a new drop never waits behind old work. Fan-out to followers runs in parallel: pushes, web push and email together.

The watcher

Polite most of the time. One read a second when it counts.

The watcher is a Python process that reads public event pages, politely, within a request budget. It never buys tickets.

The budget. Every read is counted in one ledger against a per-minute budget. Clubs are swept on a fixed clock; societies keep their own, slower clocks and give way first when the budget is tight. A fast-lane read that comes back blind (an error, a rate limit, a timeout) doubles that lane’s interval, to 2, 4, 8 and then 10 seconds, and when every page is blind the whole loop backs off.

The fast lane. Most of the time a pending night is looked at every few seconds as part of its venue’s sweep. When its release time is known, from 90 seconds before it the watcher reads just that night’s detail once a second until it flips, or three minutes pass, then every two seconds until ten minutes after. Nights with no stated time get the same one-second read from twenty seconds before to forty seconds after each round hour, 09:00 to 22:00. All lanes share a single read per second on a wall-clock grid, and while a lane is open the cold sweeps stretch out to make room for it.

Two machines. The same watcher runs on a cloud VM and on a second machine, half an interval out of phase, so their looks interleave instead of landing together. The second machine is a hot standby: every two minutes it checks the VM’s heartbeat, and if that is stale or blind, it promotes itself. Both post every observation; the backend turns them into one. A separate deadman process reads the heartbeat and raises the alarm if a watcher stops, which is the only way to tell a quiet week from a dead one.

Release times

Reading a release time out of a sentence.

The ticket platform has no release-time field. Organisers write it in the event description instead, in every style imaginable. A parser finds the sentence, strips the HTML, and resolves it to an instant in Europe/London:

“Tickets on sale Wednesday 6pm”→ Wednesday 18:00, Europe/London (BST or GMT, whichever applies)

Weekdays and “today” / “tomorrow” resolve from when the night was first listed, not from when the page happened to be re-read. A time in the past, or at or after the night itself, is thrown away, and anything ambiguous returns nothing rather than a guess.

A parsed time does three jobs: it schedules the ten-minute warning, it opens the watcher’s fast lane, and it heats that society’s polling clock. It never fires the “dropped” alert. That only ever follows an observed flip.

Flip guard

One drop, one alert.

Two feeds reading the same page half an interval apart will disagree at the moment of release: one box can still hold a stale copy for a few seconds and report “pending” after the other has seen the night go live. Committed naively, that is live → pending → live, and a second “tickets just dropped” push. The backend stops it in layers:

  • OrderEach night’s row is locked and compare-and-set on observation time. An older observation that arrives late is skipped.
  • Reversal holdLive → pending or sold out, seen within 90 s of going live, is held. It commits only if an observation at least 30 s later still agrees.
  • Quiet re-flipA night that goes buyable again within 10 minutes of a dropped or restock alert is recorded silently, never pushed twice.
  • OutboxTransitions are unique per night, kind and sequence, so the same moment cannot be queued twice.
  • SendsEvery push and email carries a fingerprint unique per person, night, kind and sequence.

The guard has its own test suite that replays both feeds interleaved around a release.

Payments

A marketplace priced at cost.

Stripe Connect onboards sellers and pays them out. There is no seller fee: the seller receives exactly their asking price.

The buyer’s booking fee is solved for, not set. It is the smallest whole-pence fee that covers the card fee on the full charge plus the payout fee on the seller’s transfer, each rounded up. Because the card fee grows with the fee itself, that is a fixed point, found in a step or two. The platform can never go negative on an order, and it keeps a penny or two of rounding at most. On a £10 ticket the fee is 49p.

Every order stores the fee model it was priced under, so changing the model never re-prices or re-pays an order that already exists. Plans are App Store subscriptions through StoreKit; ticket checkout is Stripe, because a ticket is admission to a real-world event.

Referral economics

Paid from subscriptions, never from tickets.

At cost there is nothing on a ticket order to share, and the fee code caps referral cash so that it can never turn an order into a loss. So referral money comes out of subscription revenue instead.

A referrer earns £2 a month for each friend on a paid plan, for as long as they stay, so three friends (£6) more than cover a £4.99 Drops plan. The friend’s £2 is a booking-fee credit, and credits are never turned into cash. Cash-out starts at £5 and goes through Stripe Connect.

On purpose

What it deliberately does not do.

  • Buy tickets on any ticketing platform. Auto-buy only buys ExeTix resale listings, and the watcher only reads.
  • Read faster than its budget. Errors and rate limits slow it down, never speed it up.
  • Trust a parsed release time to announce a drop. Only an observed flip does that.
  • Track anyone. No ads and no tracking; data is used to run the app.
